Since our last update, Lykn 0.6.0 has come a long way. We’ve finished the main compiler and tooling work we described in June, made the language more comfortable to use across projects, and brought the book’s 0.6 edition into alignment with the implementation. Along the way, building with Lykn—and explaining how to build with it—has continued to give us useful reasons to revisit things we thought were settled. We’re now working through that practical experience before publication.

The remaining items from June have landed. Both compilers enforce the surface/kernel boundary, with an explicit `kernel:` escape hatch where needed. `lykn lint` now checks Lykn source for idiom and style, and the guides have been reconciled with the language and toolchain. These were important pieces of the original 0.6.0 commitment, and it’s satisfying to have them in place.

Some of that work led us further into name resolution. A name can refer to a local binding, a language form, or a macro, and the compiler needs to make that distinction reliably. Both backends now follow explicit lexical binding rules, with downstream stages consuming the resolution information. The linter uses those same scope decisions, so a local function that happens to share a name with a built-in doesn’t receive advice intended for the built-in.

Working across packages has become easier, too. `lykn add` records exact-pinned dependencies, while `lykn link` and `lykn unlink` let a project use a local build during development. Local overrides also work with registry specifiers. Fresh project scaffolds now include a project-local launcher, and fixes to nested package output make the journey from creating a project to building and consuming it more dependable.

Writing real modules also suggested a few modest additions to the language. `(exports ...)` declares a module’s named exports together; grouped `bind` keeps related, sequential bindings in one place; and `cond` provides ordered predicate/result branches. These grew out of the same everyday questions that come up while writing examples: how should this module read, which values belong together, and what is the clearest way to express this choice?

The book refresh gave those questions a thorough workout. It also exposed cases where the compiler accepted something misleading or emitted invalid JavaScript. We tightened diagnostics for ambiguous method-call shapes, incomplete value-producing conditionals, malformed function parameters, and overlapping function clauses. We also repaired typed closure returns and improved macro-import errors. Each correction makes an unsuccessful first attempt a little easier to understand.

There have been practical changes around execution and distribution as well. `lykn run` now requires explicit Deno permissions instead of silently granting blanket access, and we repaired the boundaries between runtime options, the selected script, and its arguments. The Rust crate also includes the embedded compiler sources it needs. These details become particularly visible when a language leaves its own repository and starts being used elsewhere.

More recently, library experiments uncovered two further compiler defects. Native pre- and post-condition predicates needed to pass through the normal surface-expression lowering, and template output needed more careful handling of decoded backslashes and carriage returns. Both repairs now have focused regressions, independent verification, and a home on the 0.6 release branch. Following those examples through compilation and execution gave us evidence we hadn’t obtained from simpler programs.

The book’s 0.6 edition has passed its HTML and EPUB builds and its executable-example gate: 428 examples passed, with 19 deliberately skipped. The next step is to finish testing the release candidate in the projects that will consume it, work through the resulting feedback, and refresh the publication checks against the final source. We said in June that our next update would bring an invitation to try a release candidate; there has been more work between those two points than we expected. We hope this gives a useful picture of where that time has gone—and of the language taking shape through it.

In addition to the remaining compiler audit, release-candidate testing in real projects, and final publication checks, we’ve decided to begin building out Lykn’s completely optional standard library for 0.6.0. We’re starting with JSON file parsing and editing, followed by YAML support, and aiming to have the first pieces ready in the coming days. These will be separate, opt-in packages, so projects can choose the functionality they need. It’s a natural continuation of the work above: a few useful libraries to build with, and more opportunities to learn from using the language ourselves.
